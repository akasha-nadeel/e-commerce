## Project

**Golden Eagle** — a headless storefront for a Sri Lankan men's/women's T-shirt & athleisure brand. Next.js 16 (App Router) + React 19 + TypeScript + Tailwind v4. The **Shopify** backend is wired up: with store credentials in `.env.local` the catalog, cart, hosted checkout, customer accounts, and product reviews all run against Shopify; with no env set, each feature falls back to typed mock data so the app still runs standalone. The switch is **per-feature and automatic** — driven by env-detection flags (`isShopifyConfigured`, `isCustomerAuthConfigured`, `isAdminConfigured`), not a build flag.

**`README.md` and `docs/shopify-integration.md` predate the Shopify wiring.** They're feature/setup notes, not architecture references. Where they disagree with this file, this file is correct. Known conflicts: the README calls `catalog.ts` "the Shopify integration seam" (that's now `products.ts`), describes the catalog as mock-only, names the display font Archivo (the code loads Inter), and lists logo files that were deleted. The integration doc says "nothing consumes `src/lib/shopify/` yet."

## Commands

```bash
npm run dev      # dev server at http://localhost:3000
npm run build    # production build — also typechecks and runs SSG (use this to verify a change compiles)
npm run lint     # ESLint (flat config, next/core-web-vitals + next/typescript)
```

There is **no test runner** configured — `npm run build` is the typecheck/verification step, so there is no "run a single test" to reach for. To check types without a full build, `npx tsc --noEmit`; to lint one file, `npx eslint src/path/to/file.tsx` (the `lint` script is a bare `eslint` and takes no path). `docs/**` and `scripts/**` are globally ignored by ESLint.

**Never run `npm audit fix --force`.** npm "fixes" the remaining advisories by downgrading `next` to 9.3.3, which would destroy the app. Vulnerable transitive deps are raised via `overrides` in `package.json` instead, and the `//overrides` key there explains each one. The `brace-expansion` override is deliberately scoped to `typescript-estree`: a blanket override breaks ESLint.

### Environment
Copy `.env.example` → `.env.local` to connect Shopify. Each feature is gated by its own flag, so wire them up independently (all optional — with none set everything runs on mocks):
- **Catalog + cart + checkout** — `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_ACCESS_TOKEN` → `isShopifyConfigured`
- **Customer accounts** — `SHOPIFY_CUSTOMER_ACCOUNT_SHOP_ID`, `SHOPIFY_CUSTOMER_ACCOUNT_CLIENT_ID` → `isCustomerAuthConfigured`
- **Reviews** — `SHOPIFY_ADMIN_ACCESS_TOKEN` (secret) → `isAdminConfigured`
- **Studio** (`/studio`, the owner's product manager) — `STUDIO_PASSWORD` + the Admin token → `isStudioConfigured`
- `SHOPIFY_API_VERSION` (Storefront + Admin) and `SHOPIFY_CUSTOMER_ACCOUNT_API_VERSION` both default to `2025-10`.

After setting the Storefront env and restarting the dev server, hit **`/api/shopify-check`** (dev-only) to confirm the token/queries work and preview transformed products.

## Architecture

### The catalog seam — `products.ts` (entry) → `catalog.ts` (mocks) / `shopify/` (live)
The most important part of the app to understand. Three layers:

- **`src/lib/products.ts`** — the **unified entry point pages call** (`getProductBySlug`, `getAllProductSlugs`, `getCollectionProducts`, `getLatestStyles`, `getRelatedProducts`, `getAccessoryProducts`, `getRecommendedProducts`, `getAllProducts`, `getNonEmptyCollectionSlugs`). Each is `async` and returns live Shopify data when `isShopifyConfigured`, else the mock. **Route / data-fetching code must call `products.ts` — do not import `catalog.ts` or `shopify/` directly.** That indirection is what keeps the mock↔live swap a one-line env change and every consumer on a single `Product` shape.
- **`src/lib/catalog.ts`** — defines the `Product` type (+ `ProductColor`/`ProductSize`/`ProductImage`/`ProductVariant`) and holds all product data as **typed mocks**, plus the stock/backorder helpers (`isOutOfStock`, `isBackorderSize`, `queuePosition`, `BACKORDER_RESTOCK`). Merchandising metadata (ratings, review counts, `badge`, `compareAtLKR` sale prices) is derived deterministically at module load. Stock is per size variant (`ProductSize.available`); a sold-out variant reads as **backorder**, not hidden — the mock `queuePosition` stands in for the real FCFS allocation deferred to Shopify (inventory policy CONTINUE).
- **`src/lib/shopify/`** — the live half. `client.ts` (Storefront GraphQL `shopifyFetch` + `isShopifyConfigured`), `queries.ts`, `transform.ts` (maps a Storefront product onto the **same `Product` type** so consumers are unchanged; also resolves swatch colours and per-colour images), `index.ts` (async accessors + `createCart`). The Storefront token is deliberately **not** `NEXT_PUBLIC_` — `shopify/*` is **server-only**; import it only from Server Components / server code.

### Caching & revalidation — `src/lib/shopify/client.ts`
Storefront reads go through `shopifyFetch` with **ISR** (`next: { revalidate: 60 }`) plus **cache tags** (`products`, `product:<handle>`, `collection:<handle>`), so statically generated pages pick up Shopify edits within ~60s. The tags exist so a Shopify webhook *could* bust them via `revalidateTag`, but **no webhook route exists yet**. Today the only on-demand invalidation is the Studio's `updateTag` after a save; edits made in Shopify admin wait out the 60s. Cart/checkout **mutations pass `cache: "no-store"`**. The Admin client (`shopify/admin.ts`) mirrors this: tagged+revalidated reads, no-store mutations.

### Checkout — `src/lib/actions/checkout.ts`
`startCheckout` (server action) builds a Shopify cart from the cart lines' variant ids (`createCart`) and returns Shopify's **hosted checkout URL**; the client redirects there. When Shopify isn't configured, or no line carries a variant id (mock mode), it returns `null` and the client falls back to the local `/checkout` page. Which gateway the hosted checkout uses is a Shopify-side concern (see domain constraints).

### Customer accounts — `src/lib/auth/`, `/api/auth/*`
Passwordless login via the **Shopify Customer Account API** (OAuth 2.0 Authorization Code + **PKCE**, hosted by Shopify). `customer-account.ts` holds endpoints + PKCE helpers; the `/api/auth/{login,callback,logout,me}` route handlers run the handshake; `session.ts` stores tokens in **httpOnly cookies** (`cust_at`/`cust_rt`/`cust_it`/`cust_exp`). There is **no proactive refresh** — an expired access token reads as logged-out. `/account` (Server Component) reads the session and queries the customer's profile + orders. Gated by `isCustomerAuthConfigured` (`SHOPIFY_CUSTOMER_ACCOUNT_SHOP_ID` + `_CLIENT_ID`).

### Product reviews — `src/lib/reviews.ts`
Custom reviews stored as Shopify **metaobjects** (type `ge_product_review`) via the **Admin API** (`shopify/admin.ts`, server-only). Submissions (`submitReview` server action) are created as **DRAFT / pending moderation**; only `ACTIVE` metaobjects render — approve them in Shopify admin (**Content → Metaobjects**). Optional review photos upload to Shopify Files first (`shopify/files.ts`: staged upload → `fileCreate`). Gated by `reviewsEnabled` (= `isAdminConfigured`). One-time setup: `node scripts/setup-reviews-metaobject.mjs` creates the metaobject definition.

### The Studio — `/studio`, `src/lib/studio/`, `src/lib/shopify/admin-products.ts`
A simplified product manager for the store owner, who finds Shopify's own Add-product form unusable. It **writes to Shopify via the Admin API and reads nothing of its own** — Shopify stays the single source of truth, and the storefront picks the product up through the normal catalog seam. Seven inputs (name, type, audience, price, colours, sizes, stock) are expanded server-side into the ~40 fields Shopify asks for.

Its real job is **enforcing the conventions `transform.ts` depends on**, which the raw Shopify admin cannot: options named exactly `Color`/`Size`, a photo pinned to each colour's variants, swatch hexes written to `custom.color_swatches` (transform's highest-priority source, so a colour can't fall back to grey), alt text carrying the colour name (transform's *fallback* grouping path — deliberate redundancy), `productType` = department because that becomes the storefront Category, and publication to **every** sales channel so the headless Storefront token can actually see the product. Pick values from `studio/options.ts`; adding a colour or garment type there is the supported way to extend the form.

**Collection membership is set by `productType` + tags, never by joining a collection.** Every storefront collection in this store is a Shopify *smart* collection (verified live). Products cannot be added to a rule-based collection, so `productSet` passes tags and lets Shopify sort them in. `StudioType.tag` must match its collection's rule exactly — note `t-shirts` is ruled by the **singular** tag `t-shirt`, and accessories need their type tag *plus* the umbrella `accessories` tag.

The rules, as they now stand in Shopify:
- `men` — `TYPE EQUALS "Men" OR TAG EQUALS "men"`, `women` — `TYPE EQUALS "Women" OR TAG EQUALS "women"`. **These were deliberately made disjunctive (2026-07-26) so unisex products can exist.** A product has exactly one `productType`, so type alone can never put it in both departments; a `Unisex` product carries both `men` and `women` tags and joins through the tag half. Collapsing either rule back to type-only silently removes every unisex product from both department pages.
- Garment/accessory collections — `TAG EQUALS "<tag>"`.

Because Category is free-text `productType`, the Category facet in `filters.ts` orders known values and **appends unknown ones rather than filtering them out** — an allowlist there once hid `Unisex` from the filters entirely, with no error to trace.

- **`studio/auth.ts`** — passphrase (`STUDIO_PASSWORD`) exchanged for an HMAC-signed httpOnly cookie **keyed by the password itself**, so rotating the env var is the revocation mechanism. Two guards, and the distinction matters: `requireStudio()` redirects (pages), `assertStudio()` throws (actions). **Every server action starts with `assertStudio()`** (except `studioLogin`/`studioLogout`, which *are* the session boundary). Actions are POST endpoints reachable without loading the page, so gating the UI gates nothing. Login has a 5-failure/60s lockout, but it's a per-instance counter that resets when a serverless instance recycles: it slows guessing, and the real protection is a long passphrase. No password set ⇒ `isStudioConfigured` false ⇒ the routes 404; it never fails open.
- **`studio/types.ts`** — the form↔server shapes, kept out of the `server-only` module so the client boundary is safe by construction rather than by type-erasure.
- **`components/studio/ui.tsx` is the Studio's design system** — built from the storefront's own form language, not invented for the admin: `rounded-xl` inputs on a `#f7f7f8` fill with a transparent border going ink on focus (per `auth-shell.tsx`), 13px semibold labels, `#d23b3b` errors, sharp-cornered ink→gold CTAs, and the checkout's gold `#eec449` tint for notices. **Add brand values here, never inline at a call site** — the first pass scattered hexes across every Studio file. `Field` renders a `<label>`, so its children must be **phrasing content**: composite controls wrap in `<span>` (see `MoneyInput`), because a `<div>` there is invalid HTML that browsers reparse and React reports only as an opaque hydration mismatch. Same class of trap: `Logo` renders its own `<Link>` and takes an `href` — wrapping it in another produces nested `<a>`s and the identical symptom.
- **The form is ordered by data dependency, not by Shopify's field order.** Colours come *before* photos because each photo is tagged with the colour it shows; photos-first left that control with nothing to pick. The desktop layout mirrors the checkout's `[1.25fr_0.95fr]` split with a **sticky live preview** that reproduces `product-card.tsx` — the owner sees the actual card before saving. It's a deliberate visual copy, not a reuse, since `ProductCard` needs a saved `Product`; keep them in step if the card design changes.
- **Writes go through `productSet`** (`synchronous: true`) — one mutation for options, variants, prices, media and inventory — then `productVariantsBulkUpdate` to pin each colour's photo, then `publishablePublish`. Editing is a **full replace**: colours or sizes dropped from the form have their variants deleted. Removal offers **two actions with guards sized to their consequences** (`ProductActions`, edit page only — never the list, so you can't destroy a row you merely mis-tapped): *Hide* → `ARCHIVED`, reversible, one inline confirm; *Delete permanently* → `productDelete`, irreversible, requires typing DELETE. They are **separate server actions**, not one action with a boolean — a wrong argument must not be able to silently destroy data. Confirmations are inline because a native `confirm()` blocks the page and would freeze the Studio. The handle is generated once at creation and never changed, so renaming can't break links.
- **`visible: false` ⇒ Shopify `DRAFT`**, which the Storefront API cannot see at all. That's both the "prepare now, publish later" workflow and **the only safe way to exercise the form against this store** — there is no staging Shopify, so `.env.local` points at production and an ACTIVE save is instantly live on goldeneagleclothing.com.
- **Smart-collection membership is computed asynchronously — measured at ~30s.** A product therefore shows *no* collections immediately after saving, which is expected and not a tagging bug; don't "fix" it. Combined with the 60s ISR on Storefront reads, a new product can take ~90s to appear on its collection page even though its own `/products/<handle>` page is live at once.
- Photos upload **one request per photo** (`uploadStudioPhoto`) rather than with the form submit, which keeps every request under `serverActions.bodySizeLimit` regardless of photo count; client-side downscaling lives in `lib/image-resize.ts` (shared with the review form).
- Saves call **`updateTag`**, not `revalidateTag` — this is read-your-own-writes, and `updateTag` makes the next request wait for fresh data instead of serving one more stale copy.
- All four routes are **`force-dynamic`**. Non-negotiable: without it, a build that lacks `STUDIO_PASSWORD` bakes the layout's 404 into static HTML and the Studio stays unreachable in production until someone rebuilds.
- **Stock writes need `read_locations` + `write_inventory` + `read_inventory`** — granted on the `neththaru-reviews` custom app 2026-07-26, so quantities now persist (verified end-to-end). Shopify inventory is per-location, so `ProductSetInventoryInput` requires a `locationId`; the app discovers it via `locations` (hence `read_locations`) and `canWriteStock()` exposes that to the form so it can warn *before* quantities are typed. If those scopes are ever lost, inventory is deliberately left **untracked** rather than tracked-at-zero — tracked-at-zero would read as sold out site-wide.
- Note the Admin token lives on the app named **`neththaru-reviews`** (a leftover name — it started as the reviews app and grew into the general admin app). `headless-storefront` holds the *Storefront* token the public site reads through; don't touch its scopes.

### Product metafields are Admin-writable but currently Storefront-unreadable
`custom.color_swatches` / `badge` / `fit` / `fabrication` are written correctly by the Studio (verified in Admin) but **the Storefront API returns `null` for all of them**, so `transform.ts` never sees them. Since 2023 Shopify only exposes a metafield to the Storefront API if it has a *definition* granting storefront access; `scripts/setup-product-metafields.mjs` creates all four with `access: { storefront: PUBLIC_READ }` (run once, safe to re-run, and creating a definition adopts values already on existing products).

**That was done on 2026-07-26 and did not fix it.** Ruled out: the values (present in Admin), the definition (exists, linked to the metafield, `PUBLIC_READ`, matching `type`), the query shape (singular `metafield` and plural `metafields(identifiers:)` both null), the API version (2025-10 and 2025-07), staleness (~4 min of polling), and a forced product reindex via `productUpdate`. The legacy `metafieldStorefrontVisibilityCreate` escape hatch no longer exists in 2025-10. Remaining suspect is the **Storefront access token itself** — the `headless-storefront` legacy custom app's token predates the definitions, so it likely needs regenerating/reinstalling the same way the Admin app did for its inventory scopes. Don't spend time re-testing the definition; it is correct.

**Impact today is near-zero, which is why this isn't urgent.** `transform.ts` falls back metafield → native option swatch → `SWATCH_BY_NAME` → grey, but the swatch *hex* is only rendered when a colour has no image (`product-card.tsx`, `purchase-panel.tsx` both prefer `c.image`). The Studio requires a photo per colour, so every colour has an image and **the live PDP renders zero grey swatch backgrounds** (verified). The real gap is `badge`, `fit` and `fabrication`: the Studio's optional fields for those currently write values the storefront can't read, so the badge won't show and the PDP falls back to its default fit/fabric copy.

### SEO & structured data — `src/lib/seo.ts`
Site identity (URL, brand, socials, description, OG fallback) is declared **once** here and consumed by `layout.tsx`, `sitemap.ts`, `robots.ts` and every page that emits structured data. Two rules govern this layer:
- **Canonicals/`@id`s must use `https://www.goldeneagleclothing.com`.** The apex 308-redirects to `www`; pointing anything at the apex files every URL under "Page with redirect" in Search Console.
- **One `@graph` per page.** The root layout emits stable `organizationNode` (`ORG_ID`) + `websiteNode` (`WEBSITE_ID`); page-level nodes (Product, CollectionPage, BreadcrumbList) **reference those by `@id` rather than restating the brand** — that consolidation is what merges the pages into one entity. Emit via `<JsonLd>` (`components/json-ld.tsx`, escapes `<` so product copy can't break out of the `<script>`).

`productDescription()` synthesises a snippet for products whose Shopify `description` is empty (several are) strictly from real attributes — name, category, colours, price, delivery policy — so it never invents a material or fit claim; filling the description in Shopify takes over automatically. `sitemap.ts` builds from `getAllProducts()` (so it can't drift from the catalog) and omits `lastModified` in mock mode rather than faking it. Private/faceted/search routes are excluded from both the sitemap and `robots.ts`.

**Empty collections are excluded, computed from live data.** Several registered collections legitimately have no stock yet, and Google reads an empty category page as thin content or a soft 404. `getNonEmptyCollectionSlugs()` filters the sitemap, and the collection page sets `robots: noindex, follow` when it renders zero products. The noindex is needed because the home page still links to every collection. A collection re-enters the sitemap and the index automatically once a product lands in it, so don't hardcode the list. `all`/`new` are query-based, not real Shopify collections, and count as populated whenever any product exists.

**The site-wide share card is a static file**: `src/app/opengraph-image.png` (+ `.alt.txt`), built by `scripts/process-og-image.mjs`. There's no `opengraph-image.tsx`. Regenerate the card by rerunning the script, not by editing the PNG. Two constraints are baked into the script. First, WhatsApp, where this brand mostly gets shared, centre-crops previews to a near-square, so all art must stay inside the central 630×630 of the 1200×630 card. Second, librsvg has neither SF Pro nor Inter installed and falls back silently, so the text uses Arial and the script throws if the text layer renders blank. Don't also set `openGraph.images` in `layout.tsx`: that overrides the file convention and drops the auto-emitted dimensions. Product and collection pages set their own images on purpose, so a shared product previews as that product.

### Policy constants are single sources of truth — `shipping.ts`, `sizing.ts`, `collections.ts` (and `/privacy` must match reality)
These are **shared by the UI, the published policy pages and the structured data on purpose** — a schema.org rate or a policy page that disagrees with what checkout charges is a consumer-protection problem, not an inconsistency. Change the constant, never the copy at a call site.
- **`shipping.ts`** — `FREE_SHIPPING_THRESHOLD_LKR` (20 000), `RETURN_WINDOW_DAYS`, the `SHIPPING` rate table and `shippingCost()`, feeding `checkout-client.tsx`, `/shipping-returns`, the footer trust band and `seo.ts`'s `OfferShippingDetails`/`MerchantReturnPolicy`. Free shipping is **local standard only**; COD is Sri Lanka only.
- **`sizing.ts`** — `SIZE_CHART` is **deliberately empty**; `/size-guide` renders the table automatically once it's populated and shows an "email us" fallback until then (`hasSizeChart`). Set `MEASURED_AS` to match how the numbers were taken — body vs. flat-garment measurements are not interchangeable.
- **`collections.ts`** — the `/collections/[slug]` route registry, shared by the page's `generateStaticParams` and the sitemap, so a new collection is crawlable the moment it's routable. `mixed: true` exposes the extra facet. Garment-type slugs (`t-shirts`, `polo`, …) need matching Smart Collection handles in Shopify. **Never build a collection link by lowercasing a product's `category`** — category is Shopify's free-text `productType` and isn't guaranteed to name a route (`Unisex` has no page of its own, since those products live under both Men and Women). Use `collectionHrefForCategory()`, which validates against the registry and falls back to `all`. This bit twice at once: a visibly broken Back button *and* a `BreadcrumbList` `item` pointing at a 404 — the second being the worse of the two, since it gets indexed rather than noticed.
- **`/privacy` must name every data processor.** The same rule applies to the privacy policy, a published legal document. It currently names Shopify (checkout/accounts) and Vercel (hosting + Web Analytics). Adding any third-party script, pixel or service that touches visitor data means updating `src/app/privacy/page.tsx` in the same change. Vercel Web Analytics (`<Analytics />`, mounted last in `layout.tsx`) is cookieless, which is why the site has no consent banner. A cookie-setting tracker would change that. The component no-ops outside production and stays inert until Web Analytics is enabled in the Vercel dashboard.

### Faceted filtering — `src/lib/filters.ts`
Pure, dependency-free filter/sort helpers (`computeFacets`, `filterAndSort`, `filtersFromParams`, `filtersToParams`). They run on **both** server and client and (de)serialize `FilterState` to/from URL search params, so collection/search state is shareable and SSR-friendly. Facet shapes are designed to map onto Shopify's `filters`. Color names map to display "families" via `COLOR_NAME_TO_FAMILY`.

### Server/client split
- **Pages are Server Components** (`async`, `await params`). Routes that list things pair `generateStaticParams` + `generateMetadata` for SSG + per-page SEO. `src/app/products/[slug]` and `src/app/collections/[slug]` are statically generated.
- **Interactivity lives in client islands** marked `"use client"`: `cart-provider`, `site-header` (mega-menu), `collection/collection-browser`, `search/search-client`, `product/purchase-panel`, `carousel-row`. Client components that read URL search params are wrapped in `<Suspense>` by their server page (see the collection page).
- **Two API routes exist only to feed client islands.** `/api/search-products` returns a trimmed catalog JSON (`revalidate = 60`, matching the Storefront cache) that the header `search-panel` fetches **once per session** and then filters client-side for instant results — add a field there if the panel needs it, don't fetch per keystroke. `/api/shopify-check` is a **dev-only** connection probe (404s in production, never prints the token). The `/api/auth/*` handlers are the OAuth handshake, not data endpoints.

### Cross-cutting providers in `src/app/layout.tsx`
`CartProvider` wraps the whole app and holds cart state in React context (`useCart`); lines merge by `slug::colorName::size`. The cart **persists to `localStorage`** (`ge_cart_v1`) — restored in an effect *after* mount rather than a lazy `useState` initialiser, so the first client render matches the empty SSR markup and doesn't hydration-mismatch; a `hydrated` flag stops the save effect from clobbering the saved cart with `[]` on that first pass. Keep that ordering if you touch it. `MotionGate` (`src/components/motion-gate.tsx`) gates the site's scroll-reveal entrance animations so they play **once per browser session** (flag in `sessionStorage`, `ge:intro-played`); read it via `useIntroPlayed()` in any animated client component so a plain refresh or later navigation doesn't replay them. `ChromeGate` (`src/components/chrome-gate.tsx`) hides the global header/footer on "bare" routes — exact-match `BARE_ROUTES` = `/login`, `/signup`, `/checkout`, plus prefix-match `BARE_SECTIONS` = `/studio` (a whole subtree with its own chrome). Note `/account` is *not* bare. Add to `BARE_ROUTES` for a single chrome-less route, `BARE_SECTIONS` for a nested section.

### Media — `src/components/media-tile.tsx`
Renders a real `next/image` when given `src`, otherwise a labelled placeholder tile. Product hero/second-angle photos live at `public/products/<slug>.jpg` (and `-2.jpg`), generated by the `scripts/*.mjs` (sharp). Real Shopify CDN images replace these via `images[].src` with no layout change; `cdn.shopify.com` is already allowlisted in `next.config.ts`.

### Config gotchas — `next.config.ts`, `components.json`
- **`images.qualities` is an allowlist.** Next 16 only honours `quality` values enumerated there (`[75, 85, 95, 100]`). Product photography is served at `quality={100}` throughout — keep that, and add any new value to the array or Next silently ignores it.
- **`experimental.serverActions.bodySizeLimit` is `8mb`** to fit a few client-resized review photos per submission; review uploads fail above it.
- **`components.json` is aspirational — shadcn/ui is *not* installed.** There is no `lucide-react`, Radix, or CVA dependency, and `globals.css` has none of the shadcn token names. Everything in `src/components/ui/` is hand-rolled against the brand palette. Running `npx shadcn add` would pull in a parallel dependency + token system that conflicts with the existing one; write the component by hand instead. Only `cn()` (`lib/utils.ts`, clsx + tailwind-merge) follows the shadcn convention.

### Styling — Tailwind v4, CSS-first
No `tailwind.config.js`. Tokens and theme live in `src/app/globals.css` via `@import "tailwindcss"` + `@theme inline`. Brand palette: ink `#0c0c0d`, gold `#eec449` (a muted `#c79a4b` appears on a few eyebrow labels), bone `#f3f1ea`. Type stack leads with Apple's SF Pro (`-apple-system`) and falls back to **Inter** (loaded via `next/font`) — despite the README mentioning "Archivo," the code uses Inter. Path alias `@/*` → `./src/*`. CTAs use the shared `Button` primitive (`src/components/ui/button.tsx`) — sharp-cornered, ink→gold on hover, renders a `<Link>` when given `href` else a `<button>`; reuse it rather than hand-rolling button classes. Section "View All" buttons are the `ViewAll` component from the same file (bottom-centred, `accent` variant), so every section's View All stays identical. Animations use **`motion`** (the Framer Motion successor). **Scroll reveals are apple.com-style** — a uniform vertical fade-up via `ui/reveal.tsx` (`Reveal`, `APPLE_EASE`) and the product card; no directional slides or price count-ups (`count-up-price.tsx` now renders a static price). **Nav/menu opening animations keep the richer SPD-directional style** — the mega-menu (height unroll + `key`-remount replay), mobile top/bottom nav show-hide, menu sheet, search panel; don't flatten these to a plain fade. `ui/sliding-number.tsx` odometer drives the cart badge; carousels use `lib/use-carousel-drag.ts` (axis-locked touch + ease-out glide) and mobile bottom sheets use `lib/use-sheet-drag.ts` (swipe-down-to-close, armed only while the sheet's scroll content is at the top so normal scrolling still works). Gate any entrance animation behind `useIntroPlayed()` (see providers) to honour the once-per-session rule, and honour `useReducedMotion()` the way `ui/page-transition.tsx` does — return the children unanimated rather than shortening the duration.

### Theming — light default, opt-in dark (pure `#000` canvas)
Light is the default for every visitor; the header's `ThemeToggle` switches to dark, remembered per device in `localStorage` (`ge:theme`). The theme is a `data-theme` attribute on `<html>`, set **before first paint** by an inline `<head>` script (`THEME_INIT_SCRIPT`, `lib/theme.ts`) per Next's "preventing flash before hydration" guide. A `useEffect` would flash white on slow connections. That's why `<html>` carries `suppressHydrationWarning`. `lib/theme.ts` is server-safe (layout imports it); the React hook is separate in `lib/use-theme.ts`, because React's server build doesn't export client hooks.

**Every colour on the page canvas must be a theme token, never a hex.**
- **The tokens:** `canvas`, `elevated` (drawers/sheets/popovers), `surface`/`surface-2`, `fg`/`fg-1`/`fg-2`/`fg-3`, `muted`/`muted-soft`, `faint`/`faint-soft`, `line`/`line-soft`/`line-strong`, `gold-deep`, `accent`/`on-accent`/`accent-hover`, `success`, `danger`/`danger-deep`. Each is a utility (`bg-canvas`, `text-fg`, …) backed by a variable defined in `globals.css` under `:root, [data-theme="light"]` and `[data-theme="dark"]`. To add a colour, add a variable to both blocks.
- **Inverted CTAs need no extra token: `bg-fg text-canvas`.** That's ink-on-white in light and white-on-black in dark; on hover use `hover:bg-[#eec449] hover:text-ink`.
- **Primary emphasis is `accent`, not `fg`:** the View All buttons (`Button variant="accent"`, via `ViewAll`) and the nav's active/hover box. It is ink in light (identical to the inverted CTA) but **gold in dark**, at the client's request, rather than inverting to white. The other inverted CTAs (Add to Cart, Checkout, Back chip, size chips) intentionally stay `bg-fg text-canvas`.
- **Literal colours are only for content that looks the same in both themes:**
  - text or buttons on a **photo**;
  - **permanently dark sections**: footer, hero, promo banner, home campaign tiles, about hero;
  - **gold fills**: text on gold is the fixed `text-ink`;
  - third-party **brand marks**.
- **Light values are the original hexes**, verified pixel-for-pixel against production when this landed. Don't "tidy" two tokens into one: `fg-1` vs `fg-2` and `muted` vs `muted-soft` exist because merging them visibly shifted light mode.
- **Labels on light photos** (the Shop By Category cards) use `--photo-label` / `--photo-label-soft` / `--photo-shade`: dark ink and no shade in light mode, white over a top gradient in dark. The light values are the originals.
- **The page scrollbar is dark in both themes.** Browsers draw the viewport scrollbar from the *root* element's `color-scheme`, so `<html>` is pinned `dark` and the theme blocks set `--scheme` instead. `body` (and any nested `[data-theme]` island) applies `color-scheme: var(--scheme)`, so inner scroll areas and native inputs and selects still follow the theme. Don't put `color-scheme` back into the theme blocks, or light mode's scrollbar turns light again.
- **SVG colours use `currentColor` plus a text class, or a `fill-*`/`stroke-*` utility** — not `var()` inside a presentation attribute. Inline `style` objects use `var(--fg)` etc.

**Theme differences live in CSS variables, not `dark:` selectors.** The one exception is the toggle's own icon swap; the `dark` custom variant is declared for that alone. Variables re-scope cleanly inside a nested `data-theme="light"` element, but `dark:` would still match there. That nesting is how **the Studio stays light**: `studio/layout.tsx` wraps both branches, signed in and signed out, in `data-theme="light"`. Shared components such as `AuthShell` and `Logo` therefore resolve light inside it, and Studio's own components keep literal colours. `Logo`'s `onLight` variant means "on the canvas": in dark mode it inverts the black eagle to white via `--logo-on-canvas`, so no second image is needed.

Dark-mode notes:
- **Accepted limit:** product photos shot on white read as light tiles on black. That's in the photography, not something code can fix.
- **Off-canvas panels** (cart drawer, search panel, filter drawer, mobile menu sheet, bottom tab bar) must be `invisible` when closed, with `transition-[transform,visibility]`. They are only translated off-screen, so without it their shadows paint a dark band along the viewport edge, and their links stay tabbable.
- **Payment-brand marks use the brands' own reversed treatment, never light chips.** Navy ink is written `var(--mark-reverse, <brand hex>)` in `logo-marquee.tsx`. That's the real brand colour in light mode (the variable is `initial` there) and white in dark. Black pills like koko get an edge via `--mark-edge`.
